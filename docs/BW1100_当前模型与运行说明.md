# BW1100 当前模型与运行说明

当前只有一版推荐继续开发的基线：**3.4，自有 mapper＋MMAC8**。本轮有效改动是显式操作数放置，将同一份数据的容量、复制、写入和读取服务对齐。完整算子验收仍有失败，尤其是正常库自动选核的部分大权重Decode、短K注意力BMM和全部token词表投影。

## 1. 直接运行

本机不需要GPU。在项目根目录执行：

```powershell
cd 'D:\01codex_work\03_super node\compute_model'
$py = Join-Path $env:USERPROFILE '.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe'

& $py -m superpod_compute gemm --m 1024 --n 12288 --k 4096 `
  --layout right-transposed-contiguous `
  --hardware superpod_compute/data/bw1100_mapper_mmac_hardware.json `
  --policy superpod_compute/data/bw1100_mapper_mmac_policy.json `
  --backend mmac --cache .cache/bw1100_mappings.sqlite3 `
  --output results/gpt_qkv.json
```

此例为GPT配置中的QKV投影。当前结果约346.388 μs。首次执行搜索，后续同输入精确查缓存；硬件、策略、布局、模型版本改变都会改变缓存身份。

`--layout row-major-contiguous`描述A[M,K]、B[K,N]都连续的情况。`right-transposed-contiguous`描述连续W[N,K]通过转置视图成为B[K,N]的情况，即常见线性层的权重存储。它不是一个额外执行的转置kernel。目前两种布局身份已区分，完整的行距/地址相关访问效率还没有建完。

## 2. 应用层输入与模型输出

| 项目 | 当前输入或输出 |
|---|---|
| 算子输入 | 本卡M、N、K，FP16/BF16，B的存储布局 |
| 硬件输入 | 72 CU、4矩阵单元/CU、时钟、MMAC形状/服务周期、HBM/L2、Shared、寄存器分区与bank规则 |
| mapper输入 | 候选bm/bn/bk、CU分组、缓冲候选、操作数布局族与固定服务参数 |
| 不要求的输入 | 实机分块、实测时延、厂商库内核名 |
| 主要输出 | `best.duration_us`、`best.mapping`、波数、HBM/L2字节量、资源容量与代表波的服务账本 |

模型不自动做TP切分，不包含rank间通信。调用方先提供每个rank的本地算子尺寸，再把算子duration交给集群执行框架。

## 3. 注意力中的批量矩阵乘法

以32头的QK为例：

```python
import json
from superpod_compute import Hardware, Policy
from superpod_compute.batched import predict_batched_gemm

h = Hardware.load('superpod_compute/data/bw1100_mapper_mmac_hardware.json')
with open('superpod_compute/data/bw1100_mapper_mmac_policy.json', encoding='utf-8') as f:
    p = Policy(**json.load(f))

r = predict_batched_gemm(
    32, 1024, 1024, 128, h, p, transpose_b=True
)
print(r['best']['duration_us'])
print(r['best']['mapping'])
```

这是32份相互独立的矩阵乘法，分块任务合并分派到72个CU。只允许同一个head内的A/B复用，不能假设不同head共享输入。这个适配器尚未达到10%精度目标，不包含FlashAttention融合、Softmax、mask或完整attention执行序列。

## 4. 当前硬件和服务参数

| 参数 | 当前值 | 来源与用途 |
|---|---:|---|
| CU / 矩阵单元数 | 72 / 4每CU | 已提供硬件信息 |
| 计算时钟 | 1.3 GHz | 与独立服务探针的换算口径一致 |
| MMAC | 16×16×16，每单元8 cycle | 独立寄存器计算探针，未按验证案例拟合 |
| K循环控制 | 每16个K元素40 cycle | 保留3.3服务参数 |
| HBM | 1.72 TB/s | 保持原带宽，未为失败算例整体降低 |
| L2 | 8 MiB，读3768/写2990 Byte/cycle | 已提供规格 |
| Shared | 64 KiB/CU | 已提供规格 |
| Shared输入写 | 59.352 Byte/cycle/CU | 原独立写服务探针 |
| 寄存器 | 768 KiB/CU，4×192 KiB分区 | 用户补充的SIMD资源关系 |
| bank结构 | 32 bank，4 Byte/word | 独立地址探针核查 |
| 读取服务分组 | 64 lane、每lane16 Byte，8个服务组 | 当前128-bit读取族；独立地址留出16/16通过 |
| 固定设备服务 | 3.121245 μs | 保持原固定项 |

`mac_per_cell_per_cycle=1`按用户要求保留。MMAC后端直接使用指令形状和8周期服务，不从该字段计算MMAC峰值。A100的array后端仍使用自己的原有配置，本轮未改成BW1100参数。

## 5. 操作数布局如何影响分块

`policy.operand_layouts=["engine-routed"]`声明一种具体软件实现族。各矩阵单元持有自己需要的A/B副本，按lane向量包放在Shared；这些副本的写入、容量和读取都入账。HBM/L2仍只计从上级获取的本地输入，复制在CU内发生。

它会改变一个候选能不能双缓冲。例如256×384×16的操作数副本为40 KiB；双缓冲需要80 KiB，超过64 KiB的Shared，所以不能再按双缓冲的重叠速度评价它。不能只计算读取时间而忽略这些副本的存储。

bank服务按实际计划的地址分布计算，不再使用旧的统一有效读取率60 Byte/cycle。bank-free的当前计划上限为128 Byte/cycle/CU；这不表示所有Shared指令或实际库地址都能达到它。2/4/8 Byte读取、标量指令开销和实际库程序的布局需分别建模。

容量占用以输入阶段与输出阶段的最大值计算，因为完整K结束后才写C；输入操作数不与输出Shared窗口同时存活。输出仍包含累加寄存器→Shared写、L2写、L2读/HBM排空，按用户要求不单列Shared→输出寄存器的读取时间。

## 6. 更换硬件时修改哪里

先复制硬件JSON作为新目标配置，修改CU/矩阵单元、指令吞吐、时钟、内存容量/带宽、Shared及寄存器分区。如果bank结构或向量读取分组不同，还需修改`shared_bank_count`、`shared_bank_word_bytes`、`shared_wave_lanes`、`shared_read_vector_bytes`和`shared_read_phase_lanes`，不能直接照搬BW1100的访问规则。

固定设备服务、循环控制和Shared输入写有效服务带有软件与目标硬件条件，需要独立微基准或其他可靠依据；不是所有参数都能由峰值硬件规格推出。mapper会重新检查容量、分配CU和选择分块，无需提供未来机器的实测分块表。

## 7. 验证结果与未解决项

普通Prefill独立验证从8/13提高到9/13，MAPE从8.77%降至5.12%；新的4组Prefill留出3/4通过。20组Decode仍5/20，新4组Decode留出3/4。GPT四项主GEMM3/4；QK/PV和4组新增注意力留出均未收敛。

本轮没有采用输出工作量拟合常数，没有统一调慢MMAC，也没有按验证尺寸定制系数。主要待解决项是正常库执行方式的选择及服务、输出指令吞吐、跨波缓存复用与地址相关访存。

## 8. 可选的分块修正表（默认关闭）

自动 mapper 假设每个分块都按 MMAC 峰值效率运行，因此在部分形状上会选中"填充更少但实机更慢"的分块。已有实测表明，这属于分块排序误差，不是漏算某项开销：把库实际使用的分块强制给模型后，误差都能回到 10% 以内。

修正表记录 137 个已编译分块各自的 `measured/model(η=1)` 中位数，来自 10 个 prefill 校准形状、每个形状全部 kernel 的实测。开启后候选只在该表内搜索，报告时延除以该系数。

```powershell
& $py -m superpod_compute gemm --m 2304 --n 4096 --k 10880 --layout row-major-contiguous `
  --hardware superpod_compute/data/bw1100_mapper_mmac_hardware.json `
  --policy superpod_compute/data/bw1100_mapper_mmac_policy.json `
  --backend mmac --no-cache --tile-correction bw1100_tile_correction
```

- 25 个独立 prefill/GPT 形状：≤10% 的比例 16→19，MAPE 9.0%→7.9%；对实测最快 kernel 的 MAPE 9.4%→5.9%。
- 该表是经验查表：分块特征只能解释 18% 的跨分块方差，因此不能外推到未编译的分块、其他库版本或其他硬件。换硬件或换库必须重测。
- 标定为计算受限的 prefill 形状，不覆盖 decode；未开启时预测与之前完全一致。
- 重建：`tools/build_tile_correction.py`；端到端复算：`tools/validate_tile_correction.py`。
