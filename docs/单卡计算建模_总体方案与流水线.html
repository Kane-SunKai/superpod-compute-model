01 / OVERALL DESIGN

先明确模块边界，再组织一条完整计算链

应用层负责给出“本卡要算什么”。计算模型负责给出“这张卡怎么分块、怎么搬、怎么重叠，以及何时完成”。

输入：三个独立对象

GemmRequest：M、N、K，输入/输出精度；连续行主序 C=AB。
Hardware：CU、矩阵服务、各级容量、带宽和时钟。
Policy：候选分块、缓冲数、复用策略、初始数据状态、固定服务。

输出：可解释的预测

总 duration；选中分块与缓冲；各层容量与数据流量；每批输出的 H/R/S/C 时间轴和写回过程。跨卡 AllReduce 等通信由外部调度/网络模块处理。

contracts.py → api.py:predict → operators.py:GemmModel → backends.py:MmacBackend + scheduler.py:operand_pipeline

这里描述的是当前 V3.2 实现。BW1100 已启用四阶段输入/计算流水；A100仍使用原 array 后端。两种硬件路径的细节并不完全相同。
02 / GPU STRUCTURE

HBM → 全卡共享 L2 → 各 CU 的 Shared → 寄存器 → 矩阵单元

资源当前配置进入模型的方式
矩阵计算72 CU，每CU 4单元；16×16×16 MMAC；8 cycles每条8192 FLOP；按指令分组和最慢单元服务计时。1.30 GHz下整卡383.3856 TFLOP/s。
Shared / LDS64 KiB/CU；读64、写59.352 B/CU/cycleA/B暂存与双缓冲；输入读取83.2 GB/s/CU；输出写入77.158 GB/s/CU，显式加入W阶段。
寄存器768 KiB/CU聚合预算（用户资料）；预留32 KiB（设计假设）C的FP32累加区 + 1/2份A/B操作数槽 + 预留；必须放得下。
L28 MiB，全卡共用；读3768 / 写2990 B/cycle输入窗口、输出窗口与保留数据共用容量；读4.8984 TB/s、写3.887 TB/s，两个方向分别计费。
HBM约144 GiB；有效带宽1.72 TB/s输入未命中/未保留的数据，以及最终FP16输出，按实际字节数计费。

矩阵服务和LDS读取来自独立微基准；HBM/L2参数沿用现有资料。384 KiB的C与80 KiB的A/B寄存器占用由此分块推导，不是实测kernel的寄存器占用。图中的寄存器与矩阵单元连接是性能模型抽象；每线程资源分配、LDS bank冲突和完整端口竞争尚未逐指令刻画。

03 / TILING & CAPACITY

任意尺寸怎么切？先枚举，再检查容量，最后比较时间

M/N 划分独立的 C 子块。每个CU负责 bm×bn 的输出；一批安排 gm×gn 个CU。不同CU的C不重叠，所以无需跨CU合并C。
K 分段输入，C一直累加。每个面板厚度bk；K未整除时处理尾段并按矩阵指令粒度补齐计算。C保留在寄存器直到全部K完成。
联合枚举缓冲和输出片。L2、Shared、A/B寄存器各选1或2份；输出片可选4/16 KiB，输出缓冲1或2份。多缓冲增加重叠，也占用更多容量。
容量通过后，模拟整个时间轴。对每个合法方案计算H/R/S/C及写回流水；再比较A复用、B复用或不复用的遍历顺序，选模型时间最小者。
Shared输入 = nS × 2(bm+bn)bk 字节
Shared输出 = min(2bm·bn, 输出片字节数 × nO)
Shared峰值 = max(输入, 输出)，因为本实现将输入/计算与最终输出分阶段执行。
寄存器 = 4bm·bn + nV × A/B操作数寄存器字节数 + 预留
L2工作窗口 = nL × 2(gm·bm+gn·bn)bk + gm·gn × Shared输出

Shared存放“每CU一份输入子片”；不同矩阵引擎使用的A/B副本进入寄存器后需要另外预算。因此Shared输入大小与寄存器操作数大小可能不同。L2工作窗口以外的剩余容量，才允许用来保留A或B。

默认bm/bn候选16、32、64、128、192、256、384；bk候选16、32、64、128、256、512，并加入有限的形状相关候选。搜索的是这些合法方案，不是所有可能GPU程序。缓存命中使用完整输入身份，不能把一个尺寸的最优块无条件套到另一个尺寸。

04 / ONE COMPLETE GEMM

算例：A[3072,1024] × B[1024,2304]

下面按五步把参数与矩阵中的具体区域对应起来。先看完整尺寸，再确定每个CU的任务与每次输入的数据；随后接到后面的搬运/计算流水图。

参数白话含义本例对应图
M / N / K完整C的行数 / 列数 / 每个输出元素的乘加长度3072 / 2304 / 1024①
bm一个CU负责的C子块有多少行，单位：元素256行②
bn一个CU负责的C子块有多少列，单位：元素384列②
gm一批任务在M方向安排多少个CU12个③
gn一批任务在N方向安排多少个CU6个③
bk每次沿K处理多长：A取几列、B同时取几行16；总共64段④
跟踪一个CU任务：从0开始编号；改变选择后，②和④的高亮及全局索引同步更新。
把五步连起来：完整C → 按bm×bn划分输出块 → 每批安排gm×gn个CU → 每CU沿K以bk为步长读入aᵢ/bᵢ → CU内部矩阵单元更新同一C块 → 全部K结束后写回。
本例：每CU 256×384；一批12×6=72个CU；每次K=16，共64次；最终拼成3072×2304的C。

图形为分块关系示意，长宽不按真实元素比例。CU(r,c)是任务组中的逻辑位置；实际硬件调度不要求相同的物理排布。索引[start:end]包含start、不包含end。

64K面板：1024÷16
72并行CU：12×6
496 KiB每CU寄存器聚合预算使用
50.183 µs此映射的完整预测时间

把第⑤步的指令数换成计算时间

把256×384的C再分成2×2个128×192区域，每个矩阵服务单元负责一块。每个K面板对应96条16×16×16指令/单元，因此最慢单元用 96×8=768 cycles，即0.590769 µs。指令完成乘加，新的乘积直接加到已有C上。

再算每个K面板的四种服务时间

阶段本阶段数据或工作量服务公式时长
H：HBM→L2整波Aᵢ 96 KiB + Bᵢ 72 KiB =168 KiB172032 B ÷ 1.72×10¹² B/s0.100019 µs
R：L2→Shared72 CU ×20 KiB =1440 KiB，包含分发副本1474560 B ÷ 4.8984×10¹² B/s0.301029 µs

④ 缓冲什么时候能覆盖

L2 / Shared 输入槽

本例L2输入窗口只有1份，必须等Rᵢ结束才能读Hᵢ₊₁；Shared有2槽，主图分别画出偶数/奇数面板的存活区间。Sᵢ读完后，Shared槽可用于Rᵢ₊₂。

A/B寄存器槽 / C累加区

A/B有2槽，必须等Cᵢ计算完成后，Sᵢ₊₂才能覆盖同一槽。C累加区独立保留：C←C+aᵢbᵢ，i从0到63，期间不把部分C写回L2/HBM。

每个活动的开始时间 = max(输入数据就绪时间，本资源空闲时间，目标缓冲槽释放时间)
结束时间 = 开始时间 + 本阶段服务时长。
重叠由这些依赖自然产生，不能把“重叠时间”再作为一个正开销相加。

⑤ 全部K结束后，把C分片写出

每CU的FP32 C为384 KiB，最终FP16输出为192 KiB。按4 KiB/片分成48片；每轮72个CU合计288 KiB。输出有两套暂存窗口，允许“这一轮写HBM”与“下一轮写L2”重叠。

输出W阶段的依据：两轮独立Shared写微基准为59.247、59.457 B/cycle/CU，配置取均值59.352003；原64是读取带宽。采用FP16小片写Shared，转换耗时暂为0。每片4 KiB，共48片；这是mapper候选，不是硬件固定传输粒度。

每CU每片先写Shared：0.053086 µs；每轮写L2为0.075871 µs，写HBM为0.171460 µs。48轮输出流水合计 8.359060 µs。FP32→FP16转换/重排的执行服务目前没有单独校准，图中显式计入寄存器写Shared：每片0.053086 µs，再进入L2/HBM写出；Shared读回不单独计时；Shared输出峰值为每CU8 KiB。

⑥ 把完整算子的三段拼起来

总时间 = 固定设备服务 3.121245 + 64个K面板流水 38.702586 + 输出流水 8.359060
= 50.182891 µs。单个首面板H+R+S+C=1.484124 µs，后续面板重叠，因此不是64×1.484124。
此形状的既有Graph设备实测为64.709 µs，模型低估约22.45%。保留该例是为了延续可核对的完整推导，不把它包装成已达到15%的精度示例。
06 / HBM TRAFFIC REUSE

L2里保留A，下一批只从HBM搬新的B

将N从2304扩为4608，其余分块保持不变。模型按N方向依次处理两批C。两批使用同一个A；第一批读入的A面板在L2留下，第二批继续复用。

L2可保留空间 = 8192 − 744 = 7448 KiB
完整A = 3072×1024×2 B = 6144 KiB，可以保留。
第二批每个面板：HBM只读新的Bᵢ =72 KiB；L2仍向CU提供aᵢ和bᵢ，所以R/S/C不消失。

复用减少了搬运，并不一定同比减少总时间。本例S/C阶段比H更长，大部分HBM服务原本就被计算隐藏了。复用主要缩短第二批的流水启动部分；主图切换后可看到H行从A+B变成只搬B；展开微秒对照图可看到H块变窄，而C流水节奏基本不变。

如果L2放不下完整A，mapper怎么做？

代码按剩余容量计算可保留K长度：keepK = floor(剩余L2字节 / (2×A条带行数))；未覆盖完整K时向下对齐bk。后续批在已保留前缀只搬B，超出前缀继续搬A+B，因此同一批的H块宽度会变化。对称地也可保留B、沿M遍历；模型比较各方案时间。它是容量受限的计划驻留策略，并未模拟真实L2替换算法。

为忠实于当前代码，两批输出在图中顺序执行：第一批输出写回结束后才开始第二批输入。当前实现没有把不同输出批的计算/写回进一步交错。
