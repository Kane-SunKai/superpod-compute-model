## 1. 矩阵指令证据

厂商SDK `/opt/dtk/include/du_mma.hpp` 的gfx938分支将16×16×16 FP16操作映射到 `__builtin_hcu_mmac_f32_16x16x16_f16_lit_lts`。

测试源码只让矩阵输入留在寄存器，重复执行MMAC，不包含GEMM的HBM/L2搬运。改变并行block数1/72/288、每block波前1/4/8、独立累加链1/4/8、循环长度4096/16384，共54组配置，每组9次计时，只存汇总值。用两个循环长度的时间差抵消固定启动/收尾；预热提高频率稳定性，未写频率或功耗设置。全部输出逐元素检查通过。

最初16次展开仍含明显循环控制开销；改为128次展开后，汇编有(1+4+8)×128=1664条静态MMAC，证明指令未被消除。依赖链的持续间隔和高并发服务率都趋近8周期/单元/指令，四个单元并行。计时指令为`s_memtime`。频率采样的主要负载状态为1300 MHz；采样不是周期加权平均频率。

每条指令的工作量为 `2×16×16×16=8192 FLOP`。因此：

```
每矩阵单元：8192 FLOP / 8 cycle = 1024 FLOP/cycle
每CU：4 × 1024 = 4096 FLOP/cycle
整卡：72 × 4096 × 1.30e9 = 383.3856 TFLOP/s
```

独立寄存器基准饱和吞吐约382.96 TFLOP/s，与此服务模型相符。8周期是据独立微基准选择的整数服务间隔，不是用某个GEMM预测误差拟合。

采用“每指令运算量÷周期数”定义吞吐的方法可参考[AMD官方矩阵指令工具](https://github.com/ROCm/amd_matrix_instruction_calculator)。这里的**BW1100周期数来自本机实测**，未直接套用AMD其他GPU的指令时延。

## 2. 为什么不再用16×16尺寸直接决定吞吐

指令形状规定运算量，吞吐还需要服务周期。`matrix_backend=mmac`时，`instruction_m/n/k`、`instruction_issue_cycles`、`arrays_per_core`和频率决定计算服务；`mac_per_cell_per_cycle=2`只作为旧array接口的等效表示，不是对内部物理PE结构的证明，也不是MMAC后端的调速旋钮。

A100默认仍采用原`array`模型。`--backend auto`按硬件配置选择；也保留显式`array`、`peak`、`mmac`。旧MAC=1配置保留为`data/bw1100_mac1_v2.json`，完整V2复现可用Git提交75a47ba。

## 3. Shared/LDS→寄存器证据

独立测试使用16 KiB Shared数组与volatile向量读取，改变并发度及4096/16384次读取长度，共18组配置。高并发下每CU读取服务约64 B/cycle，整卡约5.98 TB/s。汇编使用`src_shared_base`，元数据标明16384字节group segment，存在64条`flat_load_dwordx4`读取；因此没有把这个吞吐误当成HBM。

这与硬件资料中约63 B/cycle的量级一致。当前选择64 B/(CU·cycle)作为持续读取服务，1.30 GHz下为83.2 GB/s/CU。这里只测读取；真实LDS读写争用与bank冲突仍没有完整建模。

## 4. 四阶段流水与缓冲寿命

```
H：HBM→L2          输入L2槽，在R完成后释放
R：L2→Shared       Shared输入槽，在S完成后释放
S：Shared→寄存器   A/B输入寄存器槽，在C完成后释放
C：矩阵MMAC       C累加寄存器保留到全部K完成
```

新增S阶段使用独立实测读取带宽，避免把L2服务直接当成操作数已经进入矩阵单元。不同K面板可以分别处于H/R/S/C阶段。输入寄存器使用1或2套，与输入分块/Shared缓冲/输出片联合搜索。

在矩阵单元间采用明确的矩形M/N划分，K不跨单元切分归约。一个引擎在寄存器中复用其A/B子片；不同引擎需要的相同A/B在Shared→寄存器时按重复读取计费。引擎分组导致的尾片不均衡也按最慢引擎计时。

例如Core块256×384、bk=16、四个引擎按2×2划分：每个引擎得到A[128×16]与B[16×192]，四个引擎合计读40 KiB。两套A/B寄存器缓冲占80 KiB，加FP32 C的384 KiB和预留32 KiB，聚合预算为496 KiB，必须满足硬件寄存器容量。

`operand_pipeline`保留四个资源的结束时刻和三个输入存储层的槽释放时刻，并与逐事件DAG验证一致。输出仍沿用V2的小片Shared/L2写回流水。当前LDS读端口与输入写服务独立建模，没有宣称任意读写模式可全速重叠。

## 5. 尚未解决的kernel差异

只采集了60组实际kernel名称，没有保留完整Profiler trace。库会选择不同MacroTile、DepthU和WorkGroup：例如常规3072×2304×1024使用MT256×384×16，而非整除130×97×270使用MT16×16×128。当前mapper搜索的是本模型允许的计划，不等同于库实际选中的计划。

另做了编译期寄存器实验。在相同`launch_bounds(512)`条件下，较大累加片出现scratch溢出，即使每CU聚合字节数看似够用。该结果只说明编译器分配约束不能被聚合容量替代；**未据此把128 VGPR直接写成BW1100不可变物理上限**。没有把缺失的编译器资源机制用任意折扣系数补齐。

因此剩余19组未达标仍需核实实际布局、每波前/线程资源分配、边界处理、额外kernel和具体调度。下一步的模型扩展应从这些机制入手。
