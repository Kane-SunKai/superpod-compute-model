## 2. 真实 LLM 采用什么函数？本次为什么只测一条路径？

AICB 的 `AiobMegatron.py` 中，线性层辅助函数的前向调用是 `torch.matmul(total_input, weight.t())`，QKV 和输出投影调用这个辅助函数。NVIDIA Megatron-LM 的普通线性前向同样可见这一调用。PyTorch 2.11 的无 bias、稠密二维 `F.linear` 走对应的转置权重 matmul 路径。[AIOB 源码](https://github.com/aliyun/aicb/blob/master/workload_generator/mocked_model/training/AiobMegatron.py)，[Megatron 源码](https://github.com/NVIDIA/Megatron-LM/blob/main/megatron/core/tensor_parallel/layers.py)，[PyTorch Linear.cpp](https://github.com/pytorch/pytorch/blob/v2.11.0/aten/src/ATen/native/Linear.cpp)。

本阶段统一使用：

```python
# X: [M,K] 连续；W: [N,K] 连续；输出: [M,N]
Y = torch.matmul(X, W.t())
```

这代表线性投影的一个前向 GEMM，不能代表完整训练、完整 Attention 或所有 LLM 框架。注意力还会出现批矩阵乘法或融合注意力；训练还有不同形状/布局的梯度 GEMM。

只做一次调用等价核查：3 个独立形状、每种调用 2 轮，`matmul(X,W.T)` 与无 bias `F.linear` 的均值差分别约 0.238%、0.0035%、0.0196%。后续 90 个校准形状及 12 个留出形状都只测 AIOB 这条路径。已有 50 组 F.linear 数据保留作回归，未重复测两套完整实验。

**函数名字不是最关键的差别，物理布局才是：**

| 项目 | 旧的连续 B 基准 | 本次 AIOB/linear 基准 |
|---|---|---|
| 数学运算 | X[M,K] × B[K,N] | X[M,K] × W.T[K,N] |
| 实际存储 | 连续 B[K,N] | 连续 W[N,K] |
| 逻辑右矩阵步长，单位为元素 | [N,1] | [1,K] |
| Python 转置本身 | 无 | 视图，不要求先复制整个 W |
| 底层库算法 | 由连续 B 的访问方式选择 | 可能选择另一种分块、向量读取与算法 |

模型过去仅按逻辑字节量计算，没有描述这一区别。现在新增 `rhs_storage` 接口并隔离缓存，但**这只是补齐输入语义，不代表已经正确预测了布局带来的所有性能影响**。

## 3. 测试如何执行，是否又变成同地址热缓存测试？

- FP16、无 bias、只前向；记录精度相关标志，不测训练反向。
- 多套独立 X/W/输出轮换，至少 4 套；X/W 总工作集至少 64 MiB，大于 8 MiB L2。大矩阵实际工作集可能远大于 64 MiB。
- 每个条件先执行至少 30 次且覆盖全部轮换槽位；捕获至少 64 次调用并覆盖完整轮换周期，再预热回放 6 次。
- GPU Event 包围整段 Graph；每轮取 25 个回放样本的 p50，再除以 Graph 中 GEMM 数量。每形状 3 轮，轮内打乱形状顺序。
- 每个形状检查首尾槽位的数值结果；数值检查通过才保存有效记录。Profiler 另外运行，只取执行元信息，不拿 Profiler 时长当测量结果。
- 新测 90×3=270 条校准记录、12×3=36 条留出记录，另有一次 12 条调用等价核查记录。

Graph 用于减少 Python 提交间隙；轮换避免同一套权重始终留在 L2。它仍是“设备连续执行、输入已在 GPU 内、单算子”的服务时间基准，**没有包含主机传输、动态批处理、通信并发或整个 LLM 的真实缓存历史**。不能把它直接当端到端服务时延。

90 组校准的三轮 p50 极差/均值：中位数 0.56%，最大 11.83%；其中 4 组超过 5%，2 组超过 10%。没有因不利结果删除这些点；它们应带上测量不确定性，后续再单独复测。该波动不足以解释普遍的几十个百分点偏差。

## 4. 为什么以前规则矩阵结果较好，这次却差？

之前 50 组主要是连续 B、同地址 Graph 稳态；现在是转置权重视图和超过 L2 的轮换工作集。验收对象已经改变，旧通过率不能直接搬过来。

17 个共同形状的核查中：旧连续 B/热缓存通过 11/17，新连续 B/热缓存仍通过 11/17，平均误差约从 9.07% 变为 9.42%；换成轮换连续 B 降至 7/17，换成线性层的轮换布局后为 1/17。**不能把所有变化归因于缓存，也不能把所有变化归因于 MMAC。**

这是一个模型对象的差别：原 mapper 求“在所给资源与数据流假设下，哪些候选分块最快”；真实库运行“该版本库实际选择的算法”。即使 N/K 都是 64 的倍数，库也不会总选到模型给出的最优分块。

例如独立校准中，固定 N=12288、K=8192，仅 M 改变：

| M | 实测均值 / μs | 执行元信息可见的 MT 标签 |
|---:|---:|---|
| 1 | 112.498 | 32×16×4 |
| 3 | 125.060 | 32×32×8 |
| 6 | 178.015 | 16×16×256 |
| 12 | 179.807 | 16×16×256 |
| 24 | 192.667 | 32×32×128 |
| 48 | 231.884 | 32×48×128 |

MT 名称只是实现线索；部分特殊算法的标签与实际线程配置并非简单一一对应。不能直接把名字中的第三维当成本模型 Shared 面板 bk，也不能仅凭名称宣称已还原完整执行计划。Profiler 的启动配置和多 kernel 情况必须另行核对。

由这些证据可以确认：**一个所有形状共用的“效率系数”不足以描述算法切换**。但单凭总 GEMM 时长，还不能唯一分辨是哪一级访存或哪个计算环节造成损失。

还对“所有形状统一乘系数 c”做了可行性核查。每个算例达到 ±10% 要求 `0.9×实测/预测 ≤ c ≤ 1.1×实测/预测`。`[1,28672,8192]` 要求 c≥2.725，而 `[2,8192,8192]` 要求 c≤1.039，交集为空。即使事后知道全部验收时间、专门选择最有利的单一 c，也最多使 27/50 通过；该系数仅作不可能性诊断，**没有用于校准模型**。统一加一个固定时长同样不可行：某大矩阵至少需加约 744 μs，而小方阵最多只能加约 1.28 μs。

## 5. MMAC 8 cycle 与官方 256 MAC/cycle，到底采用哪个？

两者不是同一个数值：一个 16³ 运算是 4096 MAC。

- 8 cycle 的持续服务间隔对应 512 MAC/cycle；4 个模型引擎/CU、72 CU、1.3 GHz 对应 383.386 TFLOP/s。
- 256 MAC/引擎/cycle 在相同计数方式下对应 191.693 TFLOP/s。

8 cycle 来自既有寄存器驻留 MMAC 独立微基准，不是把 GEMM 总时长反向拟合出来。该微基准跨 72 CU 的观测吞吐约 370.7–376.8 TFLOP/s。这说明至少需要核对厂商给出的“引擎数量、MAC/cycle、频率”的统计口径；不能擅自断言官方物理结构错误，也不能只因某个验收点更准就选一个峰值。

本阶段没有改动正式硬件文件。MMAC 后端按指令形状与服务周期计算；256 对照按每引擎 256 MAC/cycle 计算，重新完整搜索所有候选，保持访存、资源和启动服务不变。上表记录其最终误差，不能把固定原映射换公式的结果叫作完整搜索结果。

## 6. 实际修改了什么？哪些尝试没有进入正式方案？

### 已保留的轻量修正

1. 输入新增右操作数物理布局标识，输出明确列出物理形状、逻辑形状与步长。不同布局不能误命中同一缓存记录。
2. CU 分组枚举不再只考虑 72 的因数与少数方形组合，补充合法矩形前沿。例如 10×7=70 个块可以在 72 CU 中容纳，旧枚举可能遗漏；小于核心数的非整除分组也是合法方案。
3. 分块约束、寄存器驻留 C、K 面板累加、Shared 双缓冲、L2 复用、读写方向带宽与输出流水线公式保持不变。

分组修正在独立校准的 3584³ 上，把模型最优预测从约 373.727 μs 改为 284.656 μs；实测约 330.352 μs。它修正了候选覆盖问题，但不是普遍的精度补丁。**原冻结 50 组的最优预测值全部未改变**，不能宣称该修正让这 50 组通过率提高。

### 已否决的 V1 阶段服务校准

V1 使用 90 个独立校准形状，把计算、HBM、Shared 操作数交付、L2 读取分别视作有效软件服务，观察能否靠插值解释损失。硬件峰值文件未改，验收形状没有单独系数。

但它仍有两个实质问题：

1. 每个校准点从总时长反推一个阶段损失，无法唯一辨认真实瓶颈，不能把这些因子称为实测硬件带宽或物理效率。
2. 参数随形状插值，跨算法边界不能泛化；它不是“少量全局、有独立物理证据的参数”。

因此即使 50 组从 3/50 提高到 29/50，也不采用：12 组新留出仅 4/12 通过。实验实现移到 `tools/diagnostics/experimental_stage_services.py`，正式 `predict/evaluate_mapping` 与 CLI 不提供这套 profile 入口，避免误用。

另做了粗粒度模板消融：直接限制 MT 的 M/N 尺寸、降低整体计算效率、加入统一读取等待，都未使校准组整体收敛。特别是把标量指针追逐的约 417 ns 延迟直接加到面板读取，会明显恶化结果，不能当作 bulk-copy 延迟使用。58 个名字解析结果中只有 23 个通过当前启动配置核对，因此这组消融只是排查线索，不能宣称已经按真实计划完成仿真。下一步即使增加执行计划输入，也必须先验证其语义，不能期待增加几个字段便自动达到 10%。

## 8. 保持轻量模型，应如何继续？

优先补“算什么、实际按哪类算法组织”，而非继续增加每个尺寸的拟合系数：

| 待区分的可能性 | 最小验证方法 | 对方案的影响 |
|---|---|---|
| 库选 GEMV/向量归约还是 Tensor GEMM | 独立提取算法类别、启动配置及输出 tile，和几组邻近尺寸核对 | 小 M 可采用相应粗粒度工作量模型，避免一律当大块 Tensor GEMM |
| 理想 mapper 与实际 tile 不同 | 同一服务公式分别评估理想候选和已确认的实际粗粒度计划 | 分开报告“理想设计性能”与“实际库性能”，核心流水线复用 |
| 全局 K 循环尾处理 | 固定 M/N，选择独立 K 序列，观察整除与尾段的额外成本 | K-loop 步长与 Shared bk 分开；尾处理为有工作量依据的附加任务 |
| 计算与读数吞吐不能同时达到孤立峰值 | 同类别独立混合负载微基准，测共享资源争用 | 修正相应共享服务资源；不按整 GEMM 误差随意缩放 |
| 多波次启动/收尾重叠 | 在已确认算法下跨工作块数量边界测试 | 按粗粒度 wave 时间线描述，不做指令级仿真 |

其中“可选粗粒度执行计划输入”会改变应用层接口，已向用户提出确认，尚未实现。它可以由 AIOB/应用适配层一次性提供，预测运行时仍不需要 GPU；但此模式需要目标软件栈的信息，不能冒充仅凭 M/N/K 和硬件参数就能精准恢复任意库选择。

若坚持只用尺寸与硬件，则要明确：当前证据还没有建立一个能可靠预测所有实际库切换的轻量规则。不能承诺现在已解决，也不能把精度目标改成“多数通过”或事后剔除慢样本。
