为什么不能把全部差值都当“启动开销”？

普通PyTorch调用的事件区间可能含有主机提交不及时造成的GPU空闲。Graph连续执行先摊薄这部分空隙，剩下的固定设备服务才用12组独立小矩阵校准。本次估计为3.105 µs；这不是所有kernel都精确相同的物理启动常数。部分非整除矩阵仍表现出与具体库kernel有关的额外耗时。

T预测 = T输入/计算流水 + T分片输出流水 + T可配置转换 + T设备固定服务 + T显式启动项 本次BW1100显式启动项 = 0；设备固定服务由校准集得到；不把eager与Graph之差再重复加回。 Shared占用 = max(输入槽数×(bm+bn)×bk×2, min(bm×bn×2, 输出槽数×输出片字节数)) 寄存器占用 = bm×bn×4 + 预留；FP32 C仍必须完整驻留，不能用“流式”绕过该约束。 L2预算 = 输入工作窗口 + 有界输出窗口 + 计划保留的输入 ≤ L2容量。

容量公式是聚合资源模型；没有加入线程占用率/编译器寄存器分配仿真。小块输出转换执行成本尚无独立校准，默认配置为0，因此不宣称完整GPU微架构精度。

11 / HBM REUSE PIPELINE

同一个A条带复用，下一输出波只从HBM搬B

以 A[1536×1040] × B[1040×2304] 为例，72个Core按12×6组织，每Core输出128×128。一个输出波覆盖1536×768；沿K每次64，最后只剩16。输入Shared双缓冲每Core64 KiB。

大面板与Core子片对应关系

Aᵢ = A[0:1536, 64i:64(i+1)]；Bᵢ,ⱼ = B[64i:64(i+1), 768j:768(j+1)]。尾面板截断到K=1040。

每个Core取aᵢ[128×64]与bᵢ,ⱼ[64×128]，更新自己的C[128×128]。K尾片分别变为128×16与16×128。

搬运大小取决于谁已驻留

首次：192 KiB的A + 96 KiB的B = 288 KiB/面板。后续N输出波：A命中，只搬96 KiB的B。K尾面板分别为72 KiB和24 KiB。

例子中A条带占3.047 MiB，输入与输出窗口占1.125 MiB，合计小于8 MiB。此例存在可行保留空间。

关键依赖：HBM完成当前面板→L2向Core分发→矩阵单元使用；下一面板可以在另一槽搬运。A虽然不再从HBM读取，仍要从L2分发到各Core，因此L2→Core字节数不会随HBM命中一起减掉。

如果A条带放不下，怎样决定搬多少？

扣除输入、输出窗口后，用剩余L2空间保留完整K面板前缀：K保留 = floor(可用字节/(2×条带行数)/bk)×bk。若整条带能放下，则保留完整K（含尾片）。后续输出波前缀只搬B，未保留部分仍搬A+B。程序也尝试交换M/N遍历顺序、保留B，选择模型时间较短者。

这是一种显式的理想驻留计划，不等同于硬件L2自动保证命中。实际库的访问顺序、替换策略仍会影响准确性；没有将计划命中当成实测命中。

12 / STREAMED C OUTPUT

C的完整累加结果在寄存器，Shared只暂存待输出的小片

另取每Core 256×384、bk=16的例子：A/B输入双缓冲40 KiB；FP32累加C占384 KiB寄存器（另加32 KiB预留）；最终FP16 C为192 KiB。旧规则因192 KiB大于64 KiB Shared而拒绝该块。新规则按两片16 KiB输出缓冲检查，可用32 KiB Shared输出。

每片j：写L2开始 = max(该片数据就绪, L2端口空闲, 输出槽空闲) 写HBM开始 = max(该片写L2完成, HBM端口空闲) 输出槽释放 = 该片写HBM完成（本实现的保守约束） 下一片的写L2可与前一片写HBM重叠；共享传输端口配置下，两者串行计费。 最终T输出 = 最后一片完成时刻，而不是整块写L2时间 + 整块写HBM时间。

本版本仍然让一个输出波全部结束后开始下一输出波，没有凭空获得跨输出波计算重叠。C覆盖完整K，仍不产生额外的C部分和归约。Mapper在4 KiB/16 KiB输出片、1/2个输出槽间搜索，较小片可降低峰值暂存需求，但也会改变流水线填充与尾部时间。

01 / WHAT THE ORIGINAL MODEL DOES

从LLMCompass借鉴分块搜索，明确本方案的数据保存规则

原版中可借鉴的沿K建模

  • Matmul.compile_and_simulate()枚举L2/L1分块、循环顺序、阵列划分等mapping，调用simulate比较时延。
  • 检查L2容量和片上SRAM工作集；部分路径依据容量决定L2是否双缓冲。
  • 层次分块的K片段贡献到同一输出位置，复用情况与遍历顺序有关。
  • 块内矩阵执行时间可通过阵列模型及其查表获得；并非所有时间都只由一个峰值FLOP公式决定。

本方案明确补充的部分

  • FP16/BF16输入与FP32累加分开记字节数；shared、C寄存器、L2分别检查。
  • 同一Core保留C直到完整K结束；不采用额外外层部分和保存/读回流程。
  • 独立搜索L2输入槽数与Core shared输入槽数，均为1或2。
  • 以数据就绪、资源占用、缓冲释放事件推进流水；输出只写一次。
  • 新增“整算子最佳mapping缓存”，与块内cycle查表分开管理。

源码依据：本机reference_runtime/software_model/matmul.py的Mapping、compile_and_simulate、simulate；hardware_model/compute_module.py的A100配置。下文是基于这些思想整理的独立设计，不声称原版源码已经实现本文全部状态与缓存接口。

LLMCompass计算后端具体接在哪儿？

本机software_model/matmul.py中，L1TileSimulator.simulate_l1_tile_compute_cycle_count()约1312行组织阵列划分，调用约1357行的Matmul.simulate_systolic_array_cycle_count()获得阵列cycle。接入时将本Core的bm/bn/k和阵列配置传到块内服务适配器，以time=cycles/clock_hz换成秒，放入事件Cᵢ。

V1令Core内阵列的K划分因子为1，避免再引入部分和归约；对4个阵列可比较M/N划分(1,4)、(2,2)、(4,1)，再由后端选择。若今后允许阵列间split-K，其合并时间与精度必须显式定义。原L1TileSimulator还带旧的SRAM/统一word_size断言，不能原封不动当作本方案的容量规则；新容量检查由本文负责，阵列服务独立适配。

不要将整算子的compile_and_simulate()返回值直接作为Cᵢ：它包含上层搬运与调度，会与H/R事件重复计费。网页演示目前使用峰值/效率后端展示mapper运行；原版阵列LUT/Scale-Sim尚未接入这个浏览器文件。

03 / K PIPELINE

保留的完整算例：先知道A0/B0属于哪里，再看搬算重叠

这些小块从哪里来？先定位当前正在算的C00大块

完整算子是 A(3072×1024) × B(1024×2304) = C(3072×2304)。当前流水线只展开左上角的C00(1536×1152)，不是同时计算整个C。它使用A的上半部和B的左半部，再沿K方向分块。

原来的外层K大块由哪些流水线小块组成贡献到哪里
第0大段，K=0–511
A[0:1536,0:512]：1536×512
B[0:512,0:1152]：512×1152		A0、A1、A2、A3沿K拼起来就是这一A大块；B0、B1、B2、B3沿K拼起来就是这一B大块。P0 = A0×B0 + A1×B1 + A2×B2 + A3×B3；P0为1536×1152的部分和。
第1大段，K=512–1023
A[0:1536,512:1024]：1536×512
B[512:1024,0:1152]：512×1152		A4、A5、A6、A7属于后一A大块；B4、B5、B6、B7属于后一B大块。P1 = A4×B4 + A5×B5 + A6×B6 + A7×B7；最终C00 = P0 + P1。
对应之前的“两个L2大批次”：就是这里K宽度为512的两对外层大块；A0/B0只占第一对大块的第一个128宽面板，A1/B1是它的第二个面板。A0×B0、A1×B1不是算不同位置的C，而是给同一块C00贡献不同K范围的部分和。

上面的P0、P1用于说明数学分解。方案A可以在同一累加器中连续更新，不必真的单独生成或写出P0/P1；本方案不采用写出P0再读回归约的执行策略。冒号范围均为左闭右开。流水线展示的128宽HBM面板是本补全设计的分片服务粒度，不表示原版LLMCompass源码把每个512宽传输实际展开成了这8个事件。

当前波：12×9个Core并行，分别持有128×128的C；每个K面板宽128。shared使用两槽，每槽64 KiB；C累加器64 KiB，另预留32 KiB工作寄存器。

层级索引范围大小与用途

这张沿用的算例流水线展示合法依赖，条宽不代表实际µs。C中的0→128等数值取A/B全1作解释。算例保持原128×128×128分块用于教学，不预先宣称它就是下方mapper在全部候选中选出的最佳解。

04 / ARBITRARY SHAPES

任意尺寸怎么切：先划输出，再给每份输出分批提供K

符号含义尺寸或单位
M,N,K本卡完整GEMM，不要求是16或分块大小的整数倍元素数
bm,bn一个Core保留的C区域；覆盖完整Kbm×bn个输出元素
bk一次向Core提供的K长度A：bm×bk；B：bk×bn
gm,gn一波并行Core的二维排列；gm×gn≤Core总数GM=gm×bm，GN=gn×bn
L,SL2输入槽数、每Core shared输入槽数；独立选择1或2缓冲数量
dI,dA,dO输入、累加、输出元素字节数默认2 B、4 B、2 B
输出波数：ceil(M/GM) × ceil(N/GN) 每个Core负责：C[m0:min(m0+bm,M), n0:min(n0+bn,N)] 同一Core内：for k0 = 0, bk, 2bk, … < K A片 = A[m0:m1, k0:min(k0+bk,K)] B片 = B[k0:min(k0+bk,K), n0:n1] 本地C += A片×B片 完整K结束 → 转换/整理 → 写出该C区域 → 释放累加器

尾块：读写掩码与计算对齐分开

例如M=130、N=97、K=270，选择bm=64、bn=64、bk=128：输出按3×2个Core块覆盖，K为128、128、14三段。最后M块只有2行，最后N块只有33列，不能越界读写。

搬运只计有效元素。演示后端的M/N尾块仍按64×64矩阵槽执行；最后K=14按矩阵粒度16执行，缺失项补零。执行FLOP可以大于有效FLOP。这会惩罚过大的边界分块。

小尺寸与无工作情况

M=1等情况允许只启用部分Core，不能仍用整卡峰值除FLOP。矩阵候选最小16；M=1的padding损失在评分中显式出现。

M或N为0直接返回空输出；K=0且beta=0返回零填充路径，不做GEMM搜索。若要优化GEMV，需注册独立的向量后端并比较，不能把缺失实现当作已支持。

每波一份独立工作：不同波使用不同C区域。V1按波顺序完成，不让尚未完成K的输出块被换走；这避免用隐含的部分和落盘换取跨波输入复用。波内每块A被同一Core行复用、每块B被同一Core列复用。

当前波有效m×n，rm=ceil(m/bm)，rn=ceil(n/bn)，当前有效K长度为k： HBM→L2唯一输入：D_H = (m+n) × k × dI [B] L2→Core逻辑副本：D_R = (rn×m + rm×n) × k × dI [B] 该波最终输出：D_O = m × n × dO [B] 矩阵后端演示：每个活跃Core执行2×bm×bn×ceil(k/q)×q FLOP 该波计算时长取最慢活跃Core；不能除以所有108个Core再忽略空闲Core。

D_H采用波内唯一面板服务模型；D_R没有假设片上多播。V1跨波按冷读计费，不自动保留上一波全部A/B。若之后加入跨波驻留，必须将驻留字节、替换策略、初始状态及资源占用纳入候选和缓存键，而不是只删除HBM费用。

05 / BUFFERS, DEPENDENCIES & TIME

双缓冲必须同时通过容量检查与生命周期检查

Core shared输入占用：S × (bm×bk + bk×bn) × dI [B] 输出整理空间：bm×bn×dO [B] shared峰值：max(输入占用, 输出整理空间) ≤ shared预算 Core寄存器峰值：bm×bn×dA + 工作寄存器预留 ≤ 寄存器预算 L2输入槽：L × (GM×bk + bk×GN) × dI [B] L2输出预留：GM×GN×dO [B] L2保守峰值：输入槽 + 输出预留 ≤ 可用L2预算

输入与输出整理不在同一阶段，因此shared按max计峰值；C寄存器一直存活。L2这里使用保守容量上界，输出与输入都预留；不将C寄存器误计为L2中的部分和。实际L2是缓存，所谓“L2槽”是建模中的可用驻留预算，不是声称GPU提供了可随意分配的L2 scratchpad。

事件 / 资源开始条件占用 / 释放
Hᵢ：HBM→L2HBM服务空闲，L2槽i mod L可覆盖L2槽从Hᵢ开始保留到Rᵢ结束
Rᵢ：L2→Core sharedHᵢ完成，聚合L2服务空闲，shared槽i mod S可覆盖shared槽从Rᵢ开始保留到Cᵢ结束

H.start[i] = max(H资源可用, L2槽释放[i mod L]) H.end[i] = H.start[i] + α_H + D_H[i]/BW_H R.start[i] = max(H.end[i], R资源可用, shared槽释放[i mod S]) R.end[i] = R.start[i] + α_R + D_R[i]/BW_R C.start[i] = max(R.end[i], 上一K段C.end) C.end[i] = C.start[i] + matrix_backend(tile_i) L2槽释放[i mod L] = R.end[i] shared槽释放[i mod S] = C.end[i] 最后：T_wave = C.end[last] + T_epilogue + T_Core→L2 + T_L2→HBM V1算子时间：T_launch + Σ每波T_wave 上述单位统一为秒；界面显示时乘10⁶得到µs。

两个缓冲级数独立：L=2允许提前准备下一L2面板；S=2允许下一次Core输入搬运与当前计算重叠。L=2并不意味着S也能取2。S=1时必须等上一计算释放shared；L=1时必须等上一R读完L2槽。它们不是简单的“全部搬运和全部计算取max”。

为什么要同时搜bk与缓冲数：128×128、bk=128时，一个A/B输入槽64 KiB，双缓冲128 KiB；bk=256时一个槽128 KiB，只能单缓冲。后者减少K段数量，前者可能更好地隐藏搬运。不能先选最大bk，再不检查容量地打开双缓冲。若K只有一段，第二个槽没有预取收益，平局应选单缓冲。

HBM与L2可以服务不同段，但各自整卡带宽只分配一次。shared读写、阵列操作数服务若已经包含在块内后端时间里，不重复收费；若单独建模，就必须加对应资源边和竞争。V1演示器采用聚合L2服务及已折算的矩阵服务，并不额外虚构共享内存端口参数。

如果HBM填入L2与L2读出争用同一端口？

硬件profile还应声明事件经过的资源：H使用HBM与L2填入通道，R使用L2读出与Core输入通道。若填入/读出共享一个受限端口，就让H、R申请同一资源ID，并按最慢链路限制服务率；不能仍无条件重叠。输出写回也应走相同资源账本。

本页可运行V1采用“H和R为独立逻辑服务边”的简化，不模拟L2 bank冲突或读写端口竞争；该规则由schedule/backend版本固定，已进入缓存签名。正式接入目标硬件时若改成共享端口，必须更换对应调度模型并使旧结果失效。

06 / JOINT MAPPER SEARCH

Mapper搜索什么，怎样判断一个候选更好？

① 归一化请求确定精度、布局、边界、资源预算与后端版本；先查精确缓存。
② 枚举＋过滤联合枚举bm/bn/bk、gm/gn、L/S，检查三类存储和Core数量。
③ 推进事件对完整波、边界波计算H/R/C与输出；保留首段等待、末段排空。
④ 排序＋记录最小预测时间胜出；保存前5名、约束账本、签名与搜索范围。
候选轴V1可运行候选集合为什么如此
bm、bn16、32、64、128、256，加输入尺寸对齐到16且不超过256的值兼顾小尺寸、矩形、尾块；不是只试正方形
bk16、32、64、128、256、512，加K向上对齐16且不超过512的值完整K很短时可一次处理；长K循环，与槽数一起优化
gm、gnCore数的因子对，加1×1、2×2、4×4、8×8；裁到实际输出网格并去重比较横向/纵向输入复用与并行度；不固定12×9
L、S各取1、2，共4种组合同时搜索两级双缓冲，而不是容量够就强制双缓冲
累加与遍历固定full-K驻留；波内独立M/N输出，波之间row-major串行固定设计边界，避免搜索混入中间C落盘策略
for 每组(bm,bn,bk,gm,gn,L,S): if shared / registers / L2 / Core数量不合法: 丢弃 按完整波和边界波的有效尺寸分成最多4类 对每类按真实有效K长度推进H/R/C（含尾段） 计入该类波数 × 单波费用，最后加kernel启动 更新按duration排序的Top-5 选择候选集合内最小值；时间相等时优先更小shared、较少缓冲。 无可行候选 → 返回明确的约束失败，不把无穷大/零时延当作结果。

搜索加速不改变结果：波内矩阵尺寸相同的完整波只评分一次，再乘次数；边界波单独评分。很长K中的重复事件若“全部资源/槽位状态”以同一时间平移、且槽位相位相同，可精确快进重复周期；尾K段照常计算。这里不按K段数无限展开大任务。

最优的含义：当前候选集合＋当前代价模型＋当前硬件/缓存状态下的最小预测值。扩大候选、换矩阵后端、加入真实效率曲线可能改变排名；这不是全体GPU程序中的全局最优，更不是实际编译器必然生成同一分块。

正式接入时怎么提高搜索质量，而不破坏这个框架？

先用同一后端穷举本候选集建立基线；之后可按经过证明的时间下界剪枝。把LLMCompass阵列时间或实测tile表接入matrix_backend，保留事件与容量层。再扩展候选粒度、GEMV后端、多个驻留任务与跨波缓存模型，每次升级模型/搜索版本并使旧缓存失效。不要用未验证的排名启发式把结果标成穷举最优。
