## 1. warp 归约核在低行数区间高估 20%~28%

**状态**：**已关闭，不修**（2026-11-12 决定）。

加密测量已经做完、根因也清楚了，但继续建模的收益不值得：要覆盖全段就得引入
"并发拐点 + 长尾"两个尺度，而受影响的只是一个窄区间；而且现有形式的平均误差
已经是四个候选里最低的（8.9%），换成"更物理"的形式反而更差。

**实际影响**：只有当形状同时满足「warp 核（length ≤ 2048）」和「行数在 C~4C 之间」时，
误差才会到 20%~28%；这个区间之外都在 10% 以内。当前所有对外结论
（softmax prefill 4.7%、decode 1.4%、gelu 1.0%）都不落在这里。

下面保留完整的测量与分析，以备将来真要修时不用重测。

### 现象

`bw_probe/measure_band_dense.py` → `bw_probe/band_dense_20261112.json`，
三个归约长度、26 个点，3 次独立分配取最小：

| length | dtype | 行数范围 | 模型误差范围 | 平均 \|误差\| |
|---|---|---|---|---|
| 2048 | fp16 | 64 ~ 6144 | −8.9% ~ **+22.8%** | 7.9% |
| 2048 | bf16 | 128 ~ 2048 | −0.8% ~ **+21.8%** | 9.5% |
| **512** | fp16 | 256 ~ 8192 | −4.2% ~ **+28.0%** | **15.3%** |
| 4096 | fp16 | 128 ~ 4096 | −0.0% ~ +11.2% | 4.8% |

**比最初估计的范围更宽**：不只是 length=2048，length=512 同样受影响（+28%）；
而 length=4096（Gmem 核）几乎不受影响。换句话说，**问题出在 warp 核，不在某个特定长度**。

### 根因：每行成本不是常数

把 launch 扣掉，反推每个点的"每行成本"（CU-cycle），再除以它在大行数下的饱和值：

**length=2048 fp16**（饱和值 ≈ 2107 cycle/行）

| 行数 | 周期/行 | κ = p/p∞ | κ·rows |
|---|---|---|---|
| 64 | 17111 | 8.12 | **520** |
| 96 | 11353 | 5.39 | **517** |
| 128 | 8482 | 4.02 | **515** |
| 192 | 5657 | 2.68 | **515** |
| 256 | 4257 | 2.02 | **517** |
| 384 | 3714 | 1.76 | 677 |
| 512 | 2912 | 1.38 | 707 |
| 1024 | 2796 | 1.33 | 1359 |
| 2048 | 2250 | 1.07 | 2187 |
| 6144 | 1983 | 0.94 | 5782 |

`κ·rows` 在 64~256 行上**稳定在 515~520**（误差 0.5%），这是"同时有多少行在飞"的直接证据：

```
C ≈ 517 行在飞 → 72 CU 各 7.2 行 → 每个 block 32/7.2 ≈ 4.5 条 wavefront（约 288 线程）
```

**这和 `resident_wavefronts_per_core = 32` 完全自洽**，也符合 PyTorch 逐元素/归约 kernel
的典型 block 尺寸。bf16 上同样的算法给出 C ≈ 421（每 block 5.1 条 wavefront）。

**但 κ·rows 从 384 行开始往上漂**（677 / 707 / 1359 / 2187 / 5782），说明这不是一个硬性的
并发上限——行数超过 C 之后，block 之间开始争抢，每个 block 的实际耗时会变长，
同时驻留的块数也在变化。**这是两个尺度叠在一起**：
一个约 500 行的并发拐点，和一个一直延伸到十万行才完全饱和的长尾
（6144 行时每行成本仍比 131072 行的饱和值高 12%）。

### 已经排除了什么

1. **不是 dtype**：fp16 与 bf16 的误差曲线形状完全重合，只是 C 分别是 517 / 421
2. **不是测量误差**：3 次分配取最小，相邻点不自相矛盾
3. **不是内存受限**：这些形状 `t_mem` 远小于计算项
4. **不是 launch 常数**：两端都拟合得好，用的是同一个值
5. **不是某种"特定长度的怪癖"**：length=512 和 2048 两个 warp 长度都中招，length=4096 没事

### 为什么现在不修

试过的四种形式（同一批点）：

| 形式 | 平均误差 | 最大误差 |
|---|---|---|
| 加性（现在用的） | **8.9%** | 28.0% |
| 地板 `max(K·p, 吞吐)` | 12.3% | 30.2% |
| 硬并发 `L·max(1, rows/C)` | 37.9% | 55.8% |
| 平滑并发 `1+(K−1)·(C/rows)^γ` | 17.3% | 172.8% |

**没有一种能同时覆盖两端和中间。** 硬并发形式在 rows ≤ C 和 rows ≫ C 都能对上
（因为 C 就是从那段数出来的），但在 C~4C 之间低估 20~30%，因为真实过渡是渐变的。

### 下一步需要什么

要真正修，得把两个尺度分开建：

1. **并发项**：`C` 已经从数据里直接读出来了（517 / 421），不需要拟合
2. **长尾项**：每行成本从 C 一直衰减到十万行才饱和，需要知道它是随
   "每 CU 驻留块数" 还是随 "总块数 / 总容量" 变化

需要补的测量：在 length=512 和 2048 上把行数再往上延伸（8192 / 16384 / 32768 / 65536），
确认长尾的形状；同时用 PMC 抓 `occupancy` 相关的计数器，直接看每 CU 驻留了几个 block，
而不是从耗时反推。

### 算修好了的判据

- 上述 26 个点的误差全部落到 **10% 以内**（现在最大 28%）
- length=4096 的 6 个点不变差（现在 4.8%）
- 重跑 `measure_simai_models.py` / `measure_model_ops.py` 后，
  报告里的 4.7% / 1.4% / 1.0% 都不变差

## 2. 矩阵乘在大 K 形状上低估 20%~40%

**状态**：待解决（2026-11-12 记录）。影响 175B / 405B 的每层矩阵乘时间，不影响 softmax / gelu / layernorm。

### 现象

`bw_probe/measure_simai_gemms.py` → `bw_probe/simai_gemms_20261112.json`，72 个点，
剔除两个库退化点后平均 10.9%，但误差有明显的形状结构：

| 形状 | 偏差范围 |
|---|---|
| fc2（M=N=seq, K=ffn）TP=1 | 6 个模型全部偏低，−16.6% ~ −40.7%，平均 **28%** |
| 175B / 405B TP=8 的 qkv 与 fc1 | −30.5% ~ −34.2% |
| 405B TP=1 的 fc1 / fc2 | −31.1% / −27.0% |
| QKᵀ / PV（K=128 或 seq 以外的短 K） | ±6% 以内 |

共同点：**K 很大**（12288 ~ 53248）。QKᵀ 的 K=128、PV 的 K=4096，都不受影响。

### 已经排除了什么

1. **不是 dtype**：fp16 / bf16 在 3 个代表形状上差 <1%，用同一种核
2. **不是测量**：2 次独立分配取最小，相邻点自洽；大形状重复测的离散度 <2%
3. **不是库退化点**：那两个点（175B TP=1 fc1、405B TP=1 qkv）比值 >3，已单独标 †；
   本条记录的是比值 1.3~1.7 的渐变偏差
4. **不是某个模型**：6 个模型的 fc2 都偏低，误差随 ffn 增大

### 根因假设

模型的分块复用是按 `GM/GN` 的 K 保留量估算的；K 越长，实际 kernel 的 K 循环步数越多，
L2 里能留住的操作数越少，有效复用低于模型假设。模型目前没有"K 步数 × 驻留容量"这一项，
所以大 K 会系统性偏乐观。

> 更正（2026-11-13）：这个根因假设**被推翻了一半**。固定 K=16384、把 N 从 3328 扫到 26624，
> 效率几乎不动（275/216/214/217 T），所以不是 L2 驻留窗口；真正的原因是库在 K≥16384 时
> 整体掉到一个效率台阶（216 T，约模型上限的 64%）。详见第 4 条。

### 下一步需要什么

- 固定 M、N（例如 `4096 × 4096`），把 K 从 1024 扫到 53248，看每元素成本的拐点在哪；
  现有 `measure_kscan.py` / `measure_kshape.py` 可以扩展
- 同时抓 PMC 的 L2 命中率，确认是不是复用下降，而不是别的（例如 K 循环控制开销）

### 算修好了的判据

- 72 个点的 |误差| 全部 ≤15%（现在最大 40.7%）
- 6 个模型的"每层矩阵乘合计"全部 ≤10%
- 已有的 100 组回归（V3 的 10.9%）不变差

## 3. layernorm 输入 ≥200 MB 时库进入慢档，低估 30%

**状态**：**已知区间，不建模**（2026-11-13 决定）。

### 现象

`bw_probe/probe_layernorm_gap.py` → `bw_probe/layernorm_gap_20261112.json`。
hidden=16384 扫行数：4096 行 165.6 ns/行、8192 行 237.5 ns/行、16384 行 193.0 ns/行，非单调。
细扫定位台阶在约 200 MB：6400 行（200 MB）164.8 ns/行，6656 行（208 MB）276.9 ns/行。
hidden=4096 在 256 MB 时也从 200 GB/s 掉到 173 GB/s；hidden=8192 在 256 MB 掉到 153 GB/s。

### 已经排除了什么

1. **不是地址**：spacer 从 0 到 1 GB、缓冲区偏移 0~256 MB、2 GB 分配/释放后重测，
   8192×16384 都是 1946±3 µs，数据指针各不相同
2. **不是 CUDA graph**：关掉 graph 用普通循环是 2168 µs，同量级
3. **不是内存系统**：同尺寸下 `x*2` / `clone` / `sum(dim=1)` 严格线性
   （200 MB→208 MB 是 242.9→251.6 µs），只有 layernorm 从 1051 跳到 1825 µs
4. **不是形状**：同为 256 MB 的 32768×4096 同样慢（2119 µs，127 GB/s）

### 根因

同一个 kernel（`vectorized_layer_norm_kernel`）在输入超过约 200 MB 后进入第二个状态：
profiler 里同一形状逐次在 1338 / 2150 µs 之间跳（1.6~1.9×），未定位到更深的原因。

### 为什么不修

SimAI 的 layernorm 是 `(seq, hidden)`，最大的 405B 也只有 4096×16384 = 128 MB，在台阶以下；
换机器后台阶的位置和倍率都会变，拟进模型不可迁移。

### 如果将来要修

需要先确定台阶是随字节数还是随"行数 × 行长"触发（本机两者同时变化），以及是否与库版本相关。

## 4. 矩阵乘 K≥16384 时库效率掉到模型上限的 64%

**状态**：待解决（2026-11-13 记录）。这是第 2 条的根因修正。

### 现象

`bw_probe/probe_matmul_shape_law.py`，M=4096 固定：

| 形状 | 实测 | 模型预测 |
|---|---|---|
| N=6656，K=12288 | 282 T | 332 T |
| N=6656，K=16384 | **216 T** | 335 T |
| K=16384，N=3328 / 6656 / 13312 / 26624 | 275 / 216 / 214 / 217 T | 287 ~ 335 T |

按 48 个 prefill 线性层点分（`prefill_decode_20261112.json`）：

| 分类 | 点数 | 实测 | 模型 | 实测/模型 | 平均\|误差\| |
|---|---|---|---|---|---|
| K ≤ 12288 | 64 | 236 T | 254 T | 0.93 | 8% |
| K ≥ 16384 且 N ≥ 8192 | 8 | 163 T | 314 T | 0.52 | 48% |
| 全部 | 72 | 231 T | 282 T | 0.82 | 18% |

### 已经排除了什么

1. **不是 L2 复用**：固定 K=16384，N 从 3328 扫到 26624（8 倍），效率 275/216/214/217 T 基本不动
2. **不是 K 的渐变**：12288→16384 是台阶（282→216 T），不是随 K 平滑下降
3. **不是库退化点**：28 T / 41 T 那两点已单独标 †，本条是 1.3~1.5× 量级的系统偏差
4. **不是 NT 布局**：同一批形状用 NN 重测（2026-11-13），K=8192 是 311 T、K=12288 是 321 T、
   K=16384 只有 222 T——台阶在两种布局下都在，只是 NN 整体快 5~13%

### 根因假设

库的大 K mainloop 在 K 超过阈值后按 ~216 T 运行（模型流水线上限的约 64%），
模型里 `matrix_efficiency = 1.0`，没有任何随形状变化的效率项。

### 下一步需要什么

- 补测 K=12288~16384 之间（13k / 14k / 15k），确认是阶跃还是过渡，位置在哪
- 把 `matrix_efficiency` 拆成两段（K<16k / K≥16k），用 48 个点验证

### 算修好了的判据

- 48 个 prefill 线性层点 |误差| ≤15%（现在最大 48%）
- 100 组回归（V3 的 10.9%）不变差

## 6. decode 的线性层有 6 个形状只有 300~440 GB/s

**状态**：**原因已定位**（2026-11-13）：是库的 NT 布局 GEMV 路径太慢，不是模型的带宽假设错。

### 复测结果（`bw_probe/measure_nn_fastest.py` → `nn_fastest_20261113.json`）

把权重预先存成 `(K,N)`（NN 布局）重测，同一形状恢复到 1.7~1.9 TB/s 等效：

| 形状 | NT（Megatron 布局） | NN | 模型预测 |
|---|---|---|---|
| M=1, 20480×5120（13B TP1 fc1） | 566.5 µs | **132.3 µs** | 125.5 µs |
| M=1, 12288×1536（175B TP8 attn_proj） | 126.1 µs | **26.5 µs** | 25.4 µs |
| M=1, 6144×6144（22B TP1 attn_proj） | 252.9 µs | **43.9 µs** | 47.2 µs |

模型/最快的比值 0.95~1.08，说明模型预测的时间 NN 下完全可达。
只有 405B/175B TP1 的两个退化形状，NN 之后仍然差 3~5 倍（236 ms → 103 ms，模型 20 ms）。

### 现象（原始记录）

M=1 的 12 个线性层里多数能跑到 1.7~1.9 TB/s（误差 +10~19%），但这些点塌陷：
405B TP1 QKV 301 GB/s、405B TP1 fc1 439、175B TP1 fc1 401、22B TP1 attn_proj 300、
175B TP8 attn_proj 300、moe TP8 attn_proj 645。对应误差 −74% ~ −82%。

### 已经排除了什么

不是模型带宽参数（同一阶段其余点是 1.7~1.9 TB/s）；不是 dtype；不是 M
（同一个 M 下不同 N 的表现差别巨大）。

### 下一步需要什么

抓这些形状的核名与 grid/block，确认是否同一个 GEMV 变体；若是，按 (N, K) 区间建一条规则。

### 算修好了的判据

decode M=1 的矩阵乘，剔除明确标注的库塌陷点后 |误差| ≤15%。
