## 1. warp 归约核在低行数区间高估 20%~28%

**状态**：**已关闭，不修**（2026-11-12 决定）。

加密测量已经做完、根因也清楚了，但继续建模的收益不值得：要覆盖全段就得引入
"并发拐点 + 长尾"两个尺度，而受影响的只是一个窄区间；而且现有形式的平均误差
已经是四个候选里最低的（8.9%），换成"更物理"的形式反而更差。

**实际影响**：只有当形状同时满足「warp 核（length ≤ 2048）」和「行数在 C~4C 之间」时，
误差才会到 20%~28%；这个区间之外都在 10% 以内。当前所有对外结论
（softmax prefill 4.7%、decode 1.4%、gelu 1.0%）都不落在这里。

下面保留完整的测量与分析，以备将来真要修时不用重测。

### 现象

`bw_probe/measure_band_dense.py` → `bw_probe/band_dense_20261112.json`，
三个归约长度、26 个点，3 次独立分配取最小：

| length | dtype | 行数范围 | 模型误差范围 | 平均 \|误差\| |
|---|---|---|---|---|
| 2048 | fp16 | 64 ~ 6144 | −8.9% ~ **+22.8%** | 7.9% |
| 2048 | bf16 | 128 ~ 2048 | −0.8% ~ **+21.8%** | 9.5% |
| **512** | fp16 | 256 ~ 8192 | −4.2% ~ **+28.0%** | **15.3%** |
| 4096 | fp16 | 128 ~ 4096 | −0.0% ~ +11.2% | 4.8% |

**比最初估计的范围更宽**：不只是 length=2048，length=512 同样受影响（+28%）；
而 length=4096（Gmem 核）几乎不受影响。换句话说，**问题出在 warp 核，不在某个特定长度**。

### 根因：每行成本不是常数

把 launch 扣掉，反推每个点的"每行成本"（CU-cycle），再除以它在大行数下的饱和值：

**length=2048 fp16**（饱和值 ≈ 2107 cycle/行）

| 行数 | 周期/行 | κ = p/p∞ | κ·rows |
|---|---|---|---|
| 64 | 17111 | 8.12 | **520** |
| 96 | 11353 | 5.39 | **517** |
| 128 | 8482 | 4.02 | **515** |
| 192 | 5657 | 2.68 | **515** |
| 256 | 4257 | 2.02 | **517** |
| 384 | 3714 | 1.76 | 677 |
| 512 | 2912 | 1.38 | 707 |
| 1024 | 2796 | 1.33 | 1359 |
| 2048 | 2250 | 1.07 | 2187 |
| 6144 | 1983 | 0.94 | 5782 |

`κ·rows` 在 64~256 行上**稳定在 515~520**（误差 0.5%），这是"同时有多少行在飞"的直接证据：

```
C ≈ 517 行在飞 → 72 CU 各 7.2 行 → 每个 block 32/7.2 ≈ 4.5 条 wavefront（约 288 线程）
```

**这和 `resident_wavefronts_per_core = 32` 完全自洽**，也符合 PyTorch 逐元素/归约 kernel
的典型 block 尺寸。bf16 上同样的算法给出 C ≈ 421（每 block 5.1 条 wavefront）。

**但 κ·rows 从 384 行开始往上漂**（677 / 707 / 1359 / 2187 / 5782），说明这不是一个硬性的
并发上限——行数超过 C 之后，block 之间开始争抢，每个 block 的实际耗时会变长，
同时驻留的块数也在变化。**这是两个尺度叠在一起**：
一个约 500 行的并发拐点，和一个一直延伸到十万行才完全饱和的长尾
（6144 行时每行成本仍比 131072 行的饱和值高 12%）。

### 已经排除了什么

1. **不是 dtype**：fp16 与 bf16 的误差曲线形状完全重合，只是 C 分别是 517 / 421
2. **不是测量误差**：3 次分配取最小，相邻点不自相矛盾
3. **不是内存受限**：这些形状 `t_mem` 远小于计算项
4. **不是 launch 常数**：两端都拟合得好，用的是同一个值
5. **不是某种"特定长度的怪癖"**：length=512 和 2048 两个 warp 长度都中招，length=4096 没事

### 为什么现在不修

试过的四种形式（同一批点）：

| 形式 | 平均误差 | 最大误差 |
|---|---|---|
| 加性（现在用的） | **8.9%** | 28.0% |
| 地板 `max(K·p, 吞吐)` | 12.3% | 30.2% |
| 硬并发 `L·max(1, rows/C)` | 37.9% | 55.8% |
| 平滑并发 `1+(K−1)·(C/rows)^γ` | 17.3% | 172.8% |

**没有一种能同时覆盖两端和中间。** 硬并发形式在 rows ≤ C 和 rows ≫ C 都能对上
（因为 C 就是从那段数出来的），但在 C~4C 之间低估 20~30%，因为真实过渡是渐变的。

### 下一步需要什么

要真正修，得把两个尺度分开建：

1. **并发项**：`C` 已经从数据里直接读出来了（517 / 421），不需要拟合
2. **长尾项**：每行成本从 C 一直衰减到十万行才饱和，需要知道它是随
   "每 CU 驻留块数" 还是随 "总块数 / 总容量" 变化

需要补的测量：在 length=512 和 2048 上把行数再往上延伸（8192 / 16384 / 32768 / 65536），
确认长尾的形状；同时用 PMC 抓 `occupancy` 相关的计数器，直接看每 CU 驻留了几个 block，
而不是从耗时反推。

### 算修好了的判据

- 上述 26 个点的误差全部落到 **10% 以内**（现在最大 28%）
- length=4096 的 6 个点不变差（现在 4.8%）
- 重跑 `measure_simai_models.py` / `measure_model_ops.py` 后，
  报告里的 4.7% / 1.4% / 1.0% 都不变差
